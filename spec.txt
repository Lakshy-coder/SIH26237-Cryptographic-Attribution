3. End-to-End Protocol
3.1 Registration
Offline Identity Authority
  1. Generate recipient ML-KEM key pair.
  2. Generate recipient ML-DSA signing key pair.
  3. Bind public keys to identity_id and key_epoch.
  4. Issue signed identity certificate.
  5. Deliver encrypted private-key bundle to recipient agent.
  6. Server stores only public keys/certificates.
3.2 Document Encryption and Distribution
Sender
  plaintext PDF
     |
     v
random 256-bit DEK
     |
     +--> AES-256-GCM --> encrypted document
     |
     +--> for each recipient:
             ML-KEM.Encaps(recipient_kem_pk)
                     |
                     v
                 shared secret
                     |
                 HKDF -> KEK
                     |
                 AES-GCM wrap(DEK)
                     |
             recipient envelope
3.3 Decryption, Attestation, and Release
1. Recipient requests a decryption session.
2. Server creates session_id + server_nonce and checks authorization.
3. Recipient agent supplies/creates client_nonce.
4. Agent obtains the encrypted package and recipient envelope.
5. Agent decapsulates the KEM ciphertext with its ML-KEM private key.
6. Agent derives the DEK and decrypts the document locally.
7. Agent derives watermark_ref from session/document/key/nonces.
8. Agent embeds the watermark and computes artifact_sha256.
9. Agent constructs canonical DecryptionEvent.
10. Recipient agent signs DecryptionEvent with ML-DSA.
11. Signed event is sent to the Ledger Collector.
12. Validators verify event, authorization, nonce/session uniqueness and block linkage.
13. Block becomes final only after M-of-N validator endorsements.
14. Commitment proof is returned to the agent.
15. Watermarked artifact is released only after ledger finality/commit confirmation.

4.2 Key Handling
Recipient private ML-KEM and ML-DSA keys never enter PostgreSQL or the application API payloads.
For MVP, store encrypted private-key material in the recipient agent keystore.
For production evolution, expose a PKCS#11/HSM/TPM-backed key-provider interface.
Public keys and certificate fingerprints are stored server-side and used for verification.
Key epochs are retained so historical signatures remain verifiable after rotation.
Revocation blocks new decryption/grant use but does not erase or invalidate historical ledger evidence.
5. Forensic Watermark Specification
5.1 Payload
Binary payload (128 bits total for MVP)
  [0..95]     watermark_ref (96 bits)
  [96..111]   doc_tag (16 bits)
  [112..127]  CRC16

Full attribution metadata remains outside the watermark in the signed ledger event.
5.2 Token derivation
wm_ref = SHAKE256(
    session_id ||
    document_sha256 ||
    recipient_signing_key_hash ||
    client_nonce ||
    server_nonce ||
    watermark_algorithm_version,
    output_length = 12 bytes
)
5.3 Embedding strategy
Render each PDF page at a fixed, controlled DPI to a raster representation.
Apply a DWT transform and optional block-level DCT/QIM component.
Spread payload bits over many coefficients using a pseudorandom sequence.
Repeat the payload across multiple pages/tiles where capacity allows.
Use FEC/CRC and majority voting during extraction.
Reconstruct a visually equivalent PDF and compute artifact_sha256.
Do not use metadata-only watermarking as the primary channel.
For text-heavy PDFs, raster watermarking is the MVP path; native text-preserving watermarking is a future enhancement.
5.4 Extraction
Leaked PDF
  -> detect/normalize pages
  -> render at expected DPI
  -> DWT/DCT transform
  -> synchronization/pseudorandom sequence
  -> recover soft bits
  -> majority vote
  -> FEC/CRC
  -> watermark_ref + confidence
  -> ledger lookup

6.3 Validation
Verify recipient ML-DSA signature.
Verify identity certificate/key binding.
Verify recipient authorization for the document.
Reject duplicate event/session/nonce values.
Verify previous block hash and Merkle root.
Validate timestamp against local policy.
Require M-of-N validator signatures before finality.
Store the same finalized block on honest validator replicas.
Expose chain and transaction verification endpoints to investigators.

  -> B decrypts => artifact_B + event_B
  -> assert watermark_A != watermark_B
  -> assert both ledger records valid

15. Single-Prompt Antigravity Build Instruction
Paste the prompt below after attaching this document and the original PS. It is intentionally compact: it fixes the architecture, tells the coding agent to implement rather than speculate, and defines the non-negotiable acceptance path.
You are the lead engineer implementing SIH26237 from the attached Technical Build Specification and the supplied Problem Statement. Treat those documents as the source of truth. Do not invent requirements, cloud services, external APIs, or extra AI features.

GOAL
Build a real, runnable MVP that proves this exact flow:
PDF upload -> one-time AES-256-GCM encryption -> per-recipient ML-KEM-1024 key envelope -> recipient-local decryption -> unique invisible watermark -> recipient ML-DSA-65 signed decryption event -> offline permissioned quorum ledger -> release watermarked PDF -> leaked PDF upload -> watermark extraction -> ledger lookup -> signature + ledger verification -> recipient/session attribution.

ARCHITECTURE
Use:
- React + TypeScript + Vite + Tailwind
- Python 3.12 + FastAPI
- PostgreSQL
- liboqs/OQS for ML-KEM-1024 and ML-DSA-65
- cryptography for AES-256-GCM, HKDF and approved hashes
- NumPy + OpenCV + PyWavelets for raster DWT/DCT watermarking
- custom permissioned quorum-signed Merkle ledger with 3 validator nodes for MVP
- Docker Compose
- pytest + httpx

NON-NEGOTIABLE SECURITY RULES
1. Recipient private ML-KEM and ML-DSA keys never enter the application DB or API responses.
2. Recipient-local agent performs private-key operations.
3. Recipient signs a canonical DecryptionEvent containing document hash, recipient/key reference, session ID, nonces, watermark_ref and artifact hash.
4. Signed event MUST be accepted by the ledger before the watermarked document is released.
5. If ledger commit/finality fails, do not release the document.
6. Ledger must be append-only, hash-linked, Merkle-verifiable and require M-of-N validator endorsements.
7. No public blockchain, cloud KMS, SaaS identity, public NTP or runtime internet dependency.
8. Never claim absolute immutability or unremovable watermarking.
9. If watermark extraction is weak/missing or ledger evidence cannot be verified, return INCONCLUSIVE rather than guessing attribution.

IMPLEMENTATION ORDER
1. Inspect the repository and create a clean modular structure.
2. Implement crypto primitives and tests first.
3. Implement identity, authorization and recipient agent.
4. Implement document encryption/distribution and local decryption.
5. Implement watermark embed/extract round-trip on real PDFs.
6. Implement ledger nodes, Merkle root, hash chain, validator signatures and quorum.
7. Integrate the invariant: signed event -> ledger finality -> artifact release.

WATERMARK
Use a compact 128-bit payload:
[96-bit watermark_ref][16-bit doc_tag][16-bit CRC].
Derive watermark_ref with SHAKE256 from session_id + document hash + recipient signing-key hash + client_nonce + server_nonce + algorithm version. Use raster page rendering and transform-domain embedding with redundancy/FEC. The extracted token must come from the actual leaked PDF, not from the database.

LEDGER
Use 3 validators for the MVP. A leader proposes a block. Each validator independently verifies:
event signature, identity binding, authorization, uniqueness, previous hash and Merkle root. Finalize on 2-of-3 endorsements. Provide endpoints to query a transaction and verify the chain. Keep application DB state separate from ledger evidence.

BUILD BEHAVIOR
Do not stop after writing a plan. Create the files, install/build only when needed, run tests, fix errors, and leave the repo in a runnable state. Prefer a modular monolith over unnecessary microservices. Use real cryptographic operations and real watermark extraction. Avoid placeholder/mock implementations for core requirements.

DONE WHEN
- A real PDF can be distributed to at least 3 test recipients.
- Two recipients produce distinct watermarked files.
- ML-DSA signatures verify.
- Ledger records reach quorum.
- A saved leaked PDF yields the correct watermark_ref.
- Investigation returns the correct recipient/session with valid signature and valid ledger proof.
- Modifying one validator's record is detected.
- Ledger failure prevents release.
- `docker compose up` starts the system locally without internet.
- Tests pass and README explains setup/demo.

When a library/API has compatibility uncertainty, inspect installed versions and official local package docs instead of guessing. Keep code simple, explicit and testable. Do not broaden scope until the end-to-end critical path is working.
